# 历史数据迁移

将旧 Elasticsearch PVC 中的历史日志、事件和审计数据，迁移到新数据链路使用的 ClickHouse 或 OpenSearch。

可在卸载旧插件之前或之后创建 `LegacyESMigration`。卸载后创建时必须显式填写 `source.pvcRefs`。迁移读取源端 PVC，不依赖旧 Elasticsearch 工作负载保持运行。

:::warning
源端 PVC 和 PV 必须仍然存在。源端 PVC 删除、或 PV 释放并清理后，历史数据将无法迁移。
:::

创建资源前，确保新数据链路为 `Ready`、本版本迁移镜像可用，且要迁移的时间范围仍在目标表的保留期内。`source.indexScope` 支持精确索引名和 glob，且必须至少命中一个索引。

## 步骤 1：创建迁移资源

### 1.1 ClickHouse

```yaml
apiVersion: log.alauda.io/v1alpha1
kind: LegacyESMigration
metadata:
  name: platform-es-history                               # 固定的迁移名称，后续命令使用
  namespace: cpaas-system
spec:
  image: <migration-worker-image>                         # 必填；本版本提供的迁移镜像，需包含 registry 和 tag 或 digest
  source:
    # pvcRefs:                                            # 卸载后创建时必填；列出全部旧 Elasticsearch PVC
    #   - <legacy-es-pvc-0>
    #   - <legacy-es-pvc-1>
    indexScope:                                           # 必填，选择要迁移的历史索引
      - "log-workload-*"
      - "log-platform-*"
      - "log-system-*"
      - "log-kubernetes-*"
      - "event-*"
      - "audit-*"
  target:
    type: clickhouse                                      # 必须与 PlatformLogForward 一致
    secretRef:
      name: platform-default-ch-conn                      # 与 PlatformLogForward 使用同一个连接 Secret
      namespace: cpaas-system
  options:
    batchSize: 250                                        # 每批写入的文档数，1~100000；默认 250
    syncIntervalSeconds: 5                                # 每批之间的最小等待时间；不填则使用默认值（ClickHouse 为 1 秒）
    maxConcurrentJobs: 1                                  # 并发任务数；ClickHouse 始终串行（1）
```

保存为 `legacy-es-migration.yaml` 并应用：

```bash
kubectl apply -f legacy-es-migration.yaml
```

### 1.2 OpenSearch

```yaml
apiVersion: log.alauda.io/v1alpha1
kind: LegacyESMigration
metadata:
  name: platform-es-history                               # 固定的迁移名称，后续命令使用
  namespace: cpaas-system
spec:
  image: <migration-worker-image>                         # 必填；本版本提供的迁移镜像，需包含 registry 和 tag 或 digest
  source:
    # pvcRefs:                                            # 卸载后创建时必填；列出全部旧 Elasticsearch PVC
    #   - <legacy-es-pvc-0>
    #   - <legacy-es-pvc-1>
    indexScope:                                           # 必填，选择要迁移的历史索引
      - "log-workload-*"
      - "log-platform-*"
      - "log-system-*"
      - "log-kubernetes-*"
      - "event-*"
      - "audit-*"
  target:
    type: opensearch                                      # 必须与 PlatformLogForward 一致
    secretRef:
      name: platform-default-os-conn                      # 与 PlatformLogForward 使用同一个连接 Secret
      namespace: cpaas-system
  options:
    batchSize: 250                                        # 每批写入的文档数，1~100000；默认 250
    syncIntervalSeconds: 5                                # 每批之间的最小等待时间；不填则使用默认值（OpenSearch 无固定等待）
    maxConcurrentJobs: 1                                  # 并发任务数；默认 1，OpenSearch 最多 2
```

保存为 `legacy-es-migration.yaml` 并应用：

```bash
kubectl apply -f legacy-es-migration.yaml
```

## 步骤 2：等待 PrecaptureReady

观察资源状态：

```bash
kubectl -n cpaas-system get legacyesmigration platform-es-history -w
```

等待资源进入 `PrecaptureReady`。此时尚未开始复制数据。

如果旧插件尚未卸载，返回[升级文档](../upgrade/index.mdx)的步骤 2 卸载旧插件。如果旧插件已卸载，继续下一步。

:::warning
如果 phase 为 `Blocked` 或 `Failed`，请勿删除或重建迁移资源、Job、源端存储卷或新存储数据；请阅读 condition message 并联系 Alauda 支持。
:::

## 步骤 3：等待迁移成功

旧插件卸载后，worker 开始复制数据。观察同一个资源，直到 phase 为 `Succeeded`：

```bash
kubectl -n cpaas-system get legacyesmigration platform-es-history \
  -o jsonpath='{.status.phase}{"\n"}'
```

迁移运行期间，请勿修改 `PlatformLogForward` 或其连接 Secret。

## 步骤 4：校验迁移

在 ClickHouse 或 OpenSearch 中执行与生产环境相同的日志、事件和审计查询，确认历史时间范围的数据存在。

在校验完成、且清理获得批准之前，请保留受保护的旧 Elasticsearch PVC 和 PV。`Phase=Succeeded` 不代表可以释放这些存储卷。
