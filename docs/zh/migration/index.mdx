# 历史数据迁移

将旧 Elasticsearch PVC 中的历史日志、事件和审计数据，迁移到新数据链路使用的 ClickHouse 或 OpenSearch。

## 是否需要迁移

历史数据迁移是可选的。新数据链路上线后（见[升级](../upgrade/index.mdx)），它已承载切换之后写入的全部日志、事件和审计数据。本次迁移只回填仍留在旧 Elasticsearch 存储卷中的更早数据。

如果跳过，切换之前写入的数据只留在旧 Elasticsearch PVC 中，无法从 ClickHouse 或 OpenSearch 查询。一旦这些源端 PVC 和 PV 被释放（见[升级](../upgrade/index.mdx)的“保留源端存储卷”），这些历史数据将永久丢失。如果现场无需从新存储查询切换前的历史数据，可跳过本章，待新存储校验完成后释放源端存储卷。

## 前提条件

- 源端为日志 **4.3** 版本的 Elasticsearch。历史数据迁移到 4.4 目前仅支持 4.3 源端；其他源端版本暂不支持。
- 新数据链路为 `Ready`（见[升级](../upgrade/index.mdx)）。
- 源端 Elasticsearch PVC 和 PV 仍然存在，且保护完好。
- 本版本的迁移 worker 镜像。该镜像独立于 Logging 插件包单独交付——请联系 Alauda 技术支持获取与本版本匹配的镜像。与已安装 Logging 插件版本不匹配的镜像可能在数据校验后无法退出。将其填入下方的 `spec.image`。
- 要迁移的时间范围仍在目标表的保留期内。

`source.indexScope` 支持精确索引名和 glob，且必须至少命中一个索引。

在旧插件仍处于安装状态、卸载它之前创建 `LegacyESMigration`。这样 operator 会自动捕获源端 Elasticsearch 存储卷，你无需手动列出。

:::warning
源端 PVC 和 PV 必须仍然存在。源端 PVC 删除、或 PV 释放并清理后，历史数据将无法迁移。
:::

## 创建迁移资源

选择与目标存储对应的页签。两份定义仅在 `target.type`、连接 Secret 和 `options` 默认值上不同。

<Tabs>
<Tab label="ClickHouse">

```yaml
apiVersion: log.alauda.io/v1alpha1
kind: LegacyESMigration
metadata:
  name: platform-es-history                               # 固定的迁移名称，后续命令使用
  namespace: cpaas-system
spec:
  image: <migration-worker-image>                         # 必填；来自 Alauda 技术支持、与版本匹配的镜像，需包含 registry 和 tag 或 digest
  source:
    indexScope:                                           # 必填，选择要迁移的历史索引
      - "log-workload-*"
      - "log-platform-*"
      - "log-system-*"
      - "log-kubernetes-*"
      - "event-*"
      - "audit-*"
  target:
    type: clickhouse                                      # 必须与 PlatformLogForward 一致
    secretRef:
      name: platform-default-ch-conn                      # 与 PlatformLogForward 使用同一个连接 Secret
      namespace: cpaas-system
  options:
    batchSize: 250                                        # 每批写入的文档数，1~100000；默认 250
    syncIntervalSeconds: 5                                # 每批之间的最小等待时间；不填则使用默认值（ClickHouse 为 1 秒）
    maxConcurrentJobs: 1                                  # 并发任务数；ClickHouse 始终串行（1）
```

保存为 `legacy-es-migration.yaml` 并应用：

```bash
kubectl apply -f legacy-es-migration.yaml
```

</Tab>
<Tab label="OpenSearch">

```yaml
apiVersion: log.alauda.io/v1alpha1
kind: LegacyESMigration
metadata:
  name: platform-es-history                               # 固定的迁移名称，后续命令使用
  namespace: cpaas-system
spec:
  image: <migration-worker-image>                         # 必填；来自 Alauda 技术支持、与版本匹配的镜像，需包含 registry 和 tag 或 digest
  source:
    indexScope:                                           # 必填，选择要迁移的历史索引
      - "log-workload-*"
      - "log-platform-*"
      - "log-system-*"
      - "log-kubernetes-*"
      - "event-*"
      - "audit-*"
  target:
    type: opensearch                                      # 必须与 PlatformLogForward 一致
    secretRef:
      name: platform-default-os-conn                      # 与 PlatformLogForward 使用同一个连接 Secret
      namespace: cpaas-system
  options:
    batchSize: 250                                        # 每批写入的文档数，1~100000；默认 250
    syncIntervalSeconds: 5                                # 每批之间的最小等待时间；不填则使用默认值（OpenSearch 无固定等待）
    maxConcurrentJobs: 1                                  # 并发任务数；默认 1，OpenSearch 最多 2
```

保存为 `legacy-es-migration.yaml` 并应用：

```bash
kubectl apply -f legacy-es-migration.yaml
```

</Tab>
</Tabs>

:::tip
旧插件已卸载时的兜底：如果在创建本资源之前就已卸载旧插件，operator 无法再为你自动捕获源端存储卷。请在 `source.pvcRefs` 中列出承载旧 Elasticsearch StatefulSet（`cpaas-elasticsearch`、`cpaas-elasticsearch-master`）的每个保留 PVC；在它们被释放前用 `kubectl -n cpaas-system get pvc` 查找。建议在卸载前创建本资源以避免此情况。
:::

## 等待 PrecaptureReady

观察资源状态：

```bash
kubectl -n cpaas-system get legacyesmigration platform-es-history -w
```

等待资源进入 `PrecaptureReady`。此时尚未开始复制数据。

`PrecaptureReady` 表示源端已捕获、存储卷已受保护。现在卸载旧插件：按[升级](../upgrade/index.mdx)的“卸载旧 Elasticsearch 插件”执行，然后返回这里。（如果已经卸载，复制会自动继续。）

:::warning
如果 phase 为 `Blocked` 或 `Failed`，请勿删除或重建迁移资源、Job、源端存储卷或新存储数据；请阅读 condition message 并联系 Alauda 支持。
:::

## 等待迁移成功

旧插件卸载后，worker 开始复制数据。观察同一个资源，直到 phase 为 `Succeeded`：

```bash
kubectl -n cpaas-system get legacyesmigration platform-es-history \
  -o jsonpath='{.status.phase}{"\n"}'
```

迁移运行期间，请勿修改 `PlatformLogForward` 或其连接 Secret。

## 校验迁移

在 ClickHouse 或 OpenSearch 中执行与生产环境相同的日志、事件和审计查询，确认历史时间范围的数据存在。

在校验完成、且清理获得批准之前，请保留受保护的旧 Elasticsearch PVC 和 PV。`Phase=Succeeded` 不代表可以释放这些存储卷。
